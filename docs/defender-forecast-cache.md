# Exact defender-selection reuse in danger previews

Missed stack-danger forecasts previously evaluated `CvUnitCombat::SelectStackDefender` directly for every known attack. Tactical attack scoring already had an exact selector memo. Danger previews can use that memo while retaining their own final strike calculation and sequential injury ledger.

`CvDangerPlots` and `CvDangerPlotContents` scalar/outcome methods accept an optional final `StackDangerDefenderSelector` callback. Its default is `NULL`, preserving the original selector for other callers. The callback contract is an internal, behavior-preserving adapter, not a new combat rule. Friendly-city threat simulation and city bombardment retain their original selectors.

Only stable, owned tactical previews supply the adapter. Inactive, foreign, nested and invalidated contexts fall back to the original selector. Scripted movement events bypass reuse conservatively: nonquick exchanges can reach heavy-charge/morale fallback movement and city-blockade checks. Standard VP's installed `EVENTS_CAN_MOVE_INTO` option was 0 in the measured control. No `CanBeAttackedBy` API/event exists in this source; the original final next-turn attackability/event path remains untouched.

The selector key records attacker owner and ID, homogeneous defender owner, source/target plots, ranged flag, exact attacker projected wounds, and every candidate occurrence's raw ID/exact wound. It preserves duplicates. Candidate pairs are canonicalized only when the existing enabled selection rule has an ID tie-break; otherwise original order remains part of the key. City garrison selection is outside this callback and retains its ordered behavior.

Mixed-owner candidate rosters and distinct objects claiming the same owner/ID within one roster bypass the memo. Repeated occurrences of the **same** object remain supported. Native owner/ID identities refer to stable engine objects inside a fixed preview scene; this does not promise equivalence for arbitrary replacement clones across calls. Zero/one eligible defender retains the original singleton and cavalry-filter path before key building.

The existing key already projects friendly wounds to candidate IDs. Unrelated injury entries have no selector dependency: eligibility reads each candidate's wound, and exchange math receives that wound plus the separate attacker-damage argument. Raw aliases are preserved rather than owner-qualifying injury arithmetic. No HP buckets or approximate equality are introduced.

The cache returns only the chosen unit. Its exchange values are **not** reused as the danger hit: comparison uses nonquick exchange math, whereas danger subsequently performs its original quick/next-turn strike and collateral computation. Each attack still selects again after previous direct, collateral, interception and AoE damage changes the ledger.

Storage uses the existing forecast table, full-vector equality, shared entry/payload budget and FIFO policy. It adds no gameplay/search limits or new XML control. Existing `defenderHits`, `defenderMisses`, `defenderEvictions`, entry and payload counters in `PLAN_PERF` expose the reuse and any additional pressure on the scalar danger table. Native timing must establish whether saved comparison work outweighs preparation and eviction costs.

`work/test-danger-defender-cache.py` compiles the actual selector/exchange, selector memo/storage/key, complete scalar/outcome danger sequences and air/city/collateral helpers. The normalized default scalar body is byte-identical to DLL60. Deterministic engine strength/damage services cover owner aliases, outside-roster wounds, ordered ties, duplicate/null selector entries, singleton behavior, script fallback, key/leaf invalidation, nested/foreign contexts, collisions and unchanged storage bounds. Null candidates are tested on the selector; the existing full danger AoE loop assumes nonnull candidates. Complete native combat math and an identical-save replay remain necessary validation boundaries.

The bounded repeated-query control removes 19,999 of 20,000 selector evaluations while returning the same unit. That is a synthetic work count, not a native speed multiplier. The controlled native comparison uses the same save/configuration and profiler-off mode, checks retained action sequences and nonempty world censuses, and reports interior turn durations alongside cache counters.
