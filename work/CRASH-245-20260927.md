RVA0x006FF42F is STacticalAssignment copy-constructor+0x2F. Instruction `mov [esi],eax` writes1 to0x00038B60. The minidump exception explicitly identifies a write AV to this address.

Recovered active-stack return addresses map to `_Uninit_fill_n<STacticalAssignment>` -> `vector::_Ufill` -> `vector::_Insert_n` -> `vector::insert` -> `vector::push_back` -> `CvTacticalPosition::addAssignment`+0x104. The last call corresponds to `assignedMoves.write().push_back(newAssignment)` in CvTacticalAI.cpp11157 in the crashed source. These are manually recovered return addresses confirmed against matching public symbols and disassembly; not a complete optimized stack unwind.

The decisive additional evidence is `_Insert_n` frame EBP0x0014F380:

- Saved `_Newvec` atEBP-0x14 is NULL. Disassembly stores the allocation return value there immediately after the allocation call.
- `_Whereoff` atEBP-0x18 is2074; element size is112bytes; inserted count is1.
- NULL +2074*112 =0x38B60, exactly the invalid destination.
- This is a push at the end while reallocating, so prior size/capacity were2074. VC9's50% growth requests3111 elements =348432bytes (340.27KiB). The initial buffer's2074 logical entries are not13 units or6000 alternative positions: they are entries in one assignment history. Their growth deserves targeted logging and termination-rule review; the dump alone does not prove why it happened.

The VC9 STL `_Allocate` delegates to global operator new without a post-call null test. The linked new/new[] wrapper atRVA0xF620 tries an allocator hook then falls back to `MSVCR90.dll!malloc`; its fallback return is not checked or converted into bad_alloc. The caller's saved NULL is therefore direct evidence of failed allocation in this path. The lower allocator's internal failure reason is not recorded.

Crash memory markers:3560608KiB committed,605452KiB reserved,28116KiB free; largest free block380KiB. This strongly supports address-space exhaustion/fragmentation as the allocation failure reason. The largest free virtual region is not a guarantee that a heap allocation of a slightly smaller size can succeed. Neither these figures nor the crash site identify the contributor to long-term memory growth. Do not label this an upstream leak, a stacking leak or an observer leak without comparative measurements.
