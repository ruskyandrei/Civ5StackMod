# Natural-terrain AI benchmark saves

`work/StackingAINaturalTests.lua` defines helpers only. Loading it does not create units, change the game, arm events or advance turns. Root must load it by the registered physical test-script/include method; the file is too long for the earlier FireTuner single-command submission limit. No C++ changes, builds or game control were performed while preparing it.

## What the fixture changes

Setup creates tagged fixture units and declares war between the current human and one existing living AI player. It never changes plot types, terrain, rivers, features, resources, roads, improvements, technologies, cities or existing units. It selects empty, unowned land with natural passability and rejects a map without enough suitable space. Unit spawning/repositioning naturally reveals terrain, and war/fog/turn history cannot be undone by deleting units; use a disposable game and preserve a pre-fixture normal UI save. Cleanup deletes only units bearing this helper's fixture tag and ID, never an untagged unit.

Formation uses an exhausted AI archer, a nearby pikeman with one movement point and two stationary human swordsmen. It finds two adjacent choices with matching underlying terrain/feature/hill status and measures danger with the protector at its original tile, joined with the archer and on the alternative. It records river crossings, movement cost, legal direct paths and other neighboring reachable choices. It rejects Arm if protection is not actually beneficial, the protector cannot survive projected hits, or it can reach the enemy for an immediate counterattack. Natural terrain is unenclosed, so a valid fixture is not a promise that only two moves exist. Review the selected action and actual alternatives.

Dense defaults to16 AI units (8 pikeman/composite-bowman pairs) and6 human longswordsmen in3 legal two-unit stacks. It requires11 usable connected land tiles within radius3 and a surrounding area without existing units/cities/ownership/improvements. Capacity is checked on the real units; no capacity technologies are granted. This deliberately differs from the earlier edited-terrain16-versus5 fixture. Compare old/new DLLs on this new identical save, not its raw elapsed time against the old different map/scenario. `pairs` and `enemies` options can reduce the fixture if the map is too small; no silent size reduction occurs.

## Create the shared baseline through the normal UI

1. Load a fresh disposable natural map under a recorded DLL/configuration. Save the untouched game through the normal UI as a separate pre-fixture backup. Keep the same enabled mods, XML, map and game options for both runs.
2. Include the helper. `StackAINaturalTests.Try("Plan", "formation")` or `Try("Plan", "dense")` searches and reports a site without changing the game. A Tiny map can still lack enough natural land; use a larger land map rather than editing terrain.
3. Run `StackAINaturalTests.Try("Formation")` or `StackAINaturalTests.Try("Dense")`. Setup logs every unit ID, role, position, HP, movement, capacity, danger, base strengths and current defense strength scaled100. Terrain/resource/river signatures are logged in stable plot order. Formation additionally reports its measured advantage and comparable movement paths.
4. Before calling Arm, use the normal UI Save Game to save a NEW baseline, such as `StackNatural Formation Baseline` or `StackNatural Dense Baseline`. Do not overwrite the pre-fixture backup. Record the save's file hash and the loaded DLL hash externally.
5. Perform a normal UI reload of that baseline on the same DLL first. Include the helper again, call `Try("Reattach")`, then `Try("Snapshot", "baseline-reloaded")`. The log must show expected unit count, original IDs/roles/positions/HP/moves/types and setup turn, `exactSetup=true`, legal capacity and no unrelated occupants in the area. Stop and investigate any mismatch; do not regenerate a different fixture and label it the same baseline.

Fixture metadata is stored only in newly spawned units' ScriptData. Source verification confirms this field is serialized by ordinary CvUnit save/read. Reattach rebuilds Lua state from those tags, so it does not depend on unsaved Lua globals. Headers, owners, unique IDs and roles are checked. Upgrades/capture can discard unit tags; missing or replaced units are reported, never matched by appearance or location to an untagged unit. Reloading the pre-fixture save is the complete cleanup method.

## Compare DLLs on exactly that baseline

1. With the baseline loaded and reattached, call `StackAINaturalTests.Try("Arm", 1)`. It verifies the untouched saved setup again, repeats formation measurements when appropriate, and optionally adds the same temporary tactical focus. It does not end the human turn. Save the baseline BEFORE this step so the temporary focus and observer state are not part of the shared baseline.
2. Resolve ordinary research/production/unit-order prompts and press normal UI End Turn once. Existing units are not silently exhausted by this helper. The first matching pre-AI callback applies the formation fixture's movement budget once; repeated callbacks do not replenish it. Dense units retain normal movement.
3. Read `STACKNAT|AI_START`, optional `AI_END`, `HUMAN_RETURN`, unit snapshots and the game's tactical completion/cache lines. The watcher detaches after the requested return count (default1); it does not request subsequent turns. `Stop()` detaches manually.
4. Preserve Lua and tactical logs plus an optional AFTER save separately. Quit normally or stop promptly if the game is demonstrably frozen. Deploy the comparison DLL, then load the SAME pre-turn baseline through normal UI. Reinclude, Reattach, verify exact setup and Arm1 again. Never compare the second turn of the old run with the first turn of the new DLL.

Identical saves retain natural terrain, RNG and the surrounding game state. Damage can vary if code changes alter legal choices; this is a result to record, not a reason to mutate the baseline. Resource-requiring spawned units can have strategic-resource penalties: actual strength/danger measurements and the shared save are authoritative rather than nominal unit stats.

For each run record DLL/save/XML hashes, initial/final unit records, all AI search durations and position counts, cache hit/miss/entry/payload diagnostics, total turn interval, unit losses, capacity violations, outsider interference and whether useful protective pairs formed. Formation success requires the archer to remain on its original tile, the protector to join, human threats to stay stationary and the archer's projected danger to fall. Dense completion alone is not a protection or performance pass.

## Bounded monitoring

Arm1 is the compact one-turn monitor. For more general progress observation, the separately prepared `StackingAITurnMonitor.Start(n)` is also available; neither helper drives autoplay or blocks on a polling loop. PlayerEndTurnCompleted is optional in VP, so AI transitions and return to the human are fallback markers. Use external log timestamps, process responsiveness and CPU to detect a real stall. Do not leave a frozen high-CPU game running while waiting for an in-game watchdog: that watchdog shares the stalled game thread. The earlier25-second dense turn is context, not a reason to wait indefinitely. The companion `work/AI-TURN-MONITOR.md` describes the external stop/investigation criterion.
